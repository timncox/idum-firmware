# IDUM v0.99 Code Walkthrough

This is a source-derived map of the imported v0.99 firmware. It is meant to preserve how the current firmware works before we start changing behavior.

## Big Picture

IDUM is a real-time gate/CV processor. It reads one clock input, four trigger/gate inputs, four analog controls, a mode button, a loop button, a loop gate, and a cycle switch. It then either passes gates through or applies one of eight mutation modes for a probabilistically selected number of clock steps.

The Arduino sketch is split into many `.ino` tabs, but it is effectively one large global-state program. Nearly all runtime state lives in `a00_Variables.ino`; individual files mutate that state in a fixed order from `loop()`.

The main loop order is:

1. Tick cooperative software timers.
2. Read inputs.
3. Detect edges and timing information.
4. Select the current mode.
5. Record or play the looper.
6. Decide whether modifications start/end/continue.
7. Handle the hidden menu.
8. Calculate and write outputs.

## Startup

`setup()` in `a10_Setup.ino` performs hardware and saved-state initialization:

- `assignPins()` configures all pins as inputs/outputs.
- `displayFirmwareVersion(2)` flashes the version code on the mode LEDs.
- `Serial.begin(9600)` is only called if `printEnable` is set.
- `initializeEEPROM()` reads options and active modes if EEPROM byte `0` contains `Q`; otherwise it writes defaults.
- `initializeIntervals()` resets mode-boundary interval state.
- `initializeHardwareInterrupts()` attaches rising-edge handlers to trigger inputs 1-4.
- `dTimer.every(1, displayTimer)` starts the cooperative display refresh timer.

The `arduino-timer` library used here is cooperative, not a hardware interrupt. Timer callbacks only run when `loop()` calls `dTimer.tick()` and `cTimer.tick()`.

## Hardware Assumptions

Inputs and outputs are inverted by hardware buffers:

- Gate input reads are negated: `clockIn = !digitalReadFast(clockPin)`.
- Gate output writes are inverted: writing `LOW` turns an output gate on, writing `HIGH` turns it off.

The module uses an Arduino Nano Every daughterboard with an ATmega4809 MCU. The default build target is `arduino:megaavr:nona4809:mode=off`, matching upstream notes for register emulation set to `None`.

## Input Pipeline

`readInputs()` in `a30_ReadInputs.ino` calls:

- `readGateInputs()` to sample clock, trigger, loop, cycle, and button inputs.
- `readAnalogInputs()` to sample mode/probability/length/parameter ADCs and invert them with `1024 - analogRead(...)`.
- `scaleCVInputs()` to quantize length and parameter values with hand-tuned hysteresis.
- `handleFreezeParam()` to either continuously copy parameter values to all channels or freeze them during active modifications.

Length scaling:

- `lengthPosition` is quantized to 0-7 from `lengRead`.
- `lengthResolution` selects direct 1-8, even, or power-of-two mappings.

Parameter scaling:

- `unscaledParam` is quantized to 0-15 from `paramRead`.
- `paramResolution` maps that into `ratchetAmount` using `odd`, `even`, or `powerOf2` lookup tables.

## Edge and Timing Pipeline

`edgeDetect()` in `a31_EdgeDetect.ino` is one of the most important files.

It derives:

- rising/falling edges for the clock and four trigger inputs
- debounced loop button/gate events
- debounced mode button press/release and long-hold menu entry
- last clock interval and last trigger intervals
- last trigger falling times for hold/gate-extension behavior
- derived x2 and x4 clock ticks
- choke flags that gate whether modified outputs are allowed to fire

The x4 clock is generated by comparing elapsed time since the most recent clock edge against `0`, `1/4`, `1/2`, and `3/4` of `lastClockInterval`. This is used heavily by loop recording and break mode.

## Mode Selection

`chooseMode()` in `a50_ChooseMode.ino` does three jobs:

1. `checkCurrentModes()` maps the raw mode ADC to `modeDialPosition` and lets a short mode-button press enable/disable the pointed-at mode.
2. `calculateModeBoundaries()` recomputes dynamic ADC intervals based on which modes are active.
3. `selectCurrentMode()` maps `modeRead` into a mode, with hysteresis.

Important behavior:

- `mode` does not update while a modification is active. This locks a modification to the mode that started it.
- In split mode, individual channels can use `mode1..mode4` independently.
- Active mode state is persisted to EEPROM byte `2`.

There is duplicate boundary utility code in `a50_ChooseMode.ino` and `a51_boundaryUtils.ino`. The lowercase `intervals`/`possibleModeBoundaries` path is used by current mode selection; the uppercase `INTERVALS`/`BOUNDARIES_2X` path appears to be an older or parallel helper.

## Modification State Machine

`modifyTest()` in `a60_ModifyTest.ino` decides when modifications start, continue, carry over, or end.

When the looper is off:

- `errorChecking()` clamps/reset flags.
- `calculateProbability()` runs on clock edges, generates random values, decreases probability cooldowns, and decrements active modification lengths.
- `decideModificationStatus()` compares random values to `probRead`, sets start/end/carryover flags, handles manual cancellation, and triggers cycle maintenance when needed.
- `activateModification()` samples length/parameter/mode state and initializes mode-specific state for the newly active modification.

When the looper is on:

- `loopModificationHandler()` loads recorded modification context from `paramHistory`, then conditionally reactivates it based on current probability.

Core concepts:

- `modifyLength` controls the clock/main modification.
- `modifyLength1..4` control the four trigger channels.
- In non-split mode, channel-specific state is copied from the main state.
- In split mode, channels run independent random tests and may pick independent modes.
- `originalModifyLength*` preserves the initial length for timing and scaling calculations.
- `probabilityModifier*` lowers the chance of immediately retriggering after a long modification.
- `carryOver*` detects a new modification beginning on the same clock that the previous one ends.

## Output Pipeline

`handleOutputs()` in `a90_handleOutputs.ino` has two phases:

- `calculateTriggerStates()` passes inputs through when a channel is inactive, or calls the active mode functions when modifications are active.
- `outputGates()` writes `clockState` and `trig1State..trig4State` to hardware, honoring choke flags and inverted output hardware.

Mode functions are called by iterating through all eight possible mode numbers and calling a mode if any of `mode`, `mode1`, `mode2`, `mode3`, or `mode4` match it. Each mode function then checks which specific channel is active.

## Mutation Modes

Mode numbers:

- `0` hold: left side of parameter skips/silences gates probabilistically; center passes through; right side extends gates after falling edges.
- `1` burst: emits clock-relative ratchets/divisions after each trigger.
- `2` multiply/ratchet: like burst, but each channel uses its own trigger interval instead of the clock interval.
- `3` ball: creates expanding or contracting bouncing-ball trigger bursts using loop-count timing rather than microsecond timing.
- `4` rotate: routes/scrambles trigger inputs to different outputs based on parameter position.
- `5` delay: emits delayed triggers based on ratios of each channel's trigger interval.
- `6` break: plays preset 16-step rhythm patterns from `breakBeat1`; stored values above `1` become ratchets.
- `7` skip: manipulates only the clock output by passing, ratcheting, or skipping external sequencer steps; trigger channels pass through if assigned to this mode.

Most modes also generate a short clock pulse at the beginning of a main modification:

```cpp
clockState = ((micros() - firstStepTime) < 10000);
```

## Looper

The looper is spread across:

- `a40_handleLooper.ino`
- `a41_LoopTriggers.ino`
- `a42_RecordTriggers.ino`

When the looper is off, IDUM continuously records:

- trigger history: `trigHistory[4][8][4]`
- per-step modification context: `paramHistory[5][8][4]`

The trigger history stores four trigger channels, eight clock steps, and four ticks per clock. The four ticks come from the derived x4 clock in `multiplyClocks()`.

When the looper turns on:

- `originalHistoryIndex` captures the current history ring-buffer position.
- `originalLoopOffset` makes the loop start with zero relative offset regardless of mode-knob position.
- loop counters and divider state reset.
- optional cycle-maintenance code can fire if a modification was active.

During playback:

- `calculateLooperVariables()` determines loop length, offset, speed, current tick, and current loop index.
- `sendIndexClocks()` manipulates the clock output so an attached sequencer follows loop index jumps.
- `readLoopMemory()` replaces `trig1In..trig4In` with recorded loop gates.
- `edgeDetectLoop()` recalculates trigger edges based on looper output.
- `loopModificationHandler()` uses recorded mode/parameter/length data to recreate modifications while still applying current probability.

The looper is not a simple gate repeater; it is closer to an eight-step, four-ticks-per-step event recorder with stored modification metadata.

## Menu and EEPROM

Holding the mode button for about one second toggles menu mode. While in menu mode:

- mode position 0 toggles `analogClock`
- positions 1-3 set parameter resolution
- positions 4-6 set length resolution
- position 7 toggles `splitMode`
- loop button toggles loop gate behavior

On menu exit, `saveOptions()` persists:

- EEPROM byte `1`: packed option bits
- EEPROM byte `3`: `paramResolution`
- EEPROM byte `4`: `lengthResolution`

Active modes are saved separately to EEPROM byte `2` whenever modes are toggled.

## Cycle Maintenance

The `cycle` switch tries to keep an external sequencer aligned when IDUM changes clock behavior. This code lives mostly in `a91_followUtils.ino` and `a01_timers.ino`.

Key behaviors:

- `skipSteps()` sends extra clock pulses directly to `clockOut`.
- `maintainCycle()` calculates how many clock pulses were skipped/added during a modification and starts `cTimer`.
- `slowClockTimer()` emits a background train of slow pulses until `cycleCount` reaches zero.
- `loopCycle()` performs a related catch-up behavior when leaving the looper.

This is hardware-facing and timing-sensitive. It should be treated carefully during refactors.

## Known Weirdness To Preserve Until Proven Otherwise

- The code is a single global-state machine. Many functions depend on specific loop order rather than explicit arguments.
- Hardware inversion is assumed throughout input and output code.
- Some modes use `micros()` timing; ball mode uses raw loop-iteration counters.
- `a51_boundaryUtils.ino` duplicates mode-boundary logic with uppercase globals, while active mode selection uses the lowercase version in `a50_ChooseMode.ino`.
- Several variables appear unused, legacy, or future-facing, including `doubleLength`, `modifyLengthMain`, `modeMain`, `modifyParamMain`, and parts of loop EEPROM persistence.
- `saveLoopData()` is currently a stub.
- The looper records four ticks per clock, but comments mention future higher resolution.
- Some comments say features "need to be implemented" even though v0.99 appears to partially implement them, especially split mode.

## Refactor Strategy

The safest path is to separate concerns without changing behavior first:

1. Freeze this import as a known-good build.
2. Add source maps/tests for pure-ish logic: wrapping, bit packing, boundary calculations, CV quantization.
3. Extract named state groups while preserving globals through compatibility wrappers.
4. Separate hardware I/O from musical state transitions.
5. Move mode algorithms toward channel-parameterized functions.
6. Only then change behavior.

Promising state groups:

- `HardwarePins`
- `InputState`
- `EdgeState`
- `ClockState`
- `ControlState`
- `MenuState`
- `ModeState`
- `ModificationState`
- `LooperState`
- `OutputState`
